## 结论（2026-09-09，尚未确认根因）

节点占用权与操作系统响应能力不同。用户自己的 SSH 也卡住，且新认证 SSH 与 Ray agent HTTP 同时超时，不能归因于单个终端窗口。第二次作业是否停止、GPU 是否释放仍未确认，禁止据此追加实验。任务专属 stop 请求已尝试但未收到确认。

## 已证实的启动耗时

- 第一次冷启动中，py-spy 捕获 transformers 模块扫描及 modelopt/diffusers 的包元数据扫描；进程出现 D 状态与 RPC/page wait。说明共享文件系统读取确实参与了等待。
- 第一次 SGLang 权重加载约 2 分钟；第二次约 24 秒。热缓存明显改变启动时间，不能将启动耗时混入稳态吞吐。
- 第一次服务已经就绪，但继承代理指向不可用的 127.0.0.1:27772，健康检查没有走通。直连返回 200。已停止第一次作业，并在第二次 worker 环境清空代理、设置 NO_PROXY；第二次健康检查、注册和释放推理显存成功。
- 第二次约 13:05:35（节点日志时间）提交，13:10:16 推理服务检查完成，13:12:33 八个训练 rank 开始分布式初始化。最后日志为 rank 0 参数量 8,788,850,688，尚无新的训练比较结果。

## 当前卡顿的线索与边界

1. 进程允许 CPU 为 0–15、64–79，共 32 个逻辑 CPU；启动 Ray 未显式指定 num-cpus，此前观察到约 128 个 idle worker。需要核对 Ray 实际公布资源和调度器配额，资源争用是候选原因，不是已证实根因。
2. 4 张 GPU 的 CPU NUMA affinity 设置失败。源码调用 nvmlDeviceSetCpuAffinity，只能证实 CPU 亲和性问题，不能据此断言设置了内存 membind。
3. 最后参数统计之后，Megatron get_model 路径包括模型 CUDA 搬运、BF16 转换和 DDP 参数/梯度缓冲区分配；随后才有优化器创建与 checkpoint 加载。最后日志不能精确定位到其中某条语句。
4. rollout/train offload 与 optimizer CPU offload 均启用，须检查主机及 cgroup 内存压力。尚未取得故障时 MemAvailable、memory.events、内核 OOM 日志，不能断言 OOM 或内存泄漏。
5. /tmp 所在根分区启动时只剩约 1.7 GB，Ray 提示若需要 spill 可能失败。尚未发现实际 spill 失败证据，不能断言磁盘满是此次失联根因。

## 恢复后的执行顺序

1. 先查询并必要时仅停止 a-restore-20260909-02，核实 GPU 进程和自己的 Ray 作业。此前排队的 stop 可能在恢复后执行，必须先查状态。
2. 采集 uptime、/proc/meminfo、/proc/pressure/{cpu,memory,io}、进程状态/wchan、/proc/self/status、/proc/self/cgroup、对应 cgroup 的内存限额/事件/CPU 配额和 NUMA mems；检查磁盘容量、共享挂载及可读取的内核错误。物理总内存不能替代作业内存限额。
3. 将 Ray CPU 数量限制在实际 affinity 与调度器配额内；已有集群需在确认无活动作业后按范围处理，不能仅改启动参数就声称当前集群已修复。
4. 重试前增加独立的资源采样日志，覆盖导入、推理加载、训练构建、checkpoint、首步五个阶段；先验证训练初始化，再恢复完整在线流程。临时目录迁移需要核对容量和文件系统类型。
5. 通过 correctness gate 后才运行稳态吞吐比较。当前没有可用于简历的新 GPU 数值或性能结论。
